### Champs conservés et pertes de format

Le format source brut n'est pas conservé dans une table d'archive. Le modèle
persisté comprend l'identité et la provenance d'avis (`source_event`), les lots,
parties, CPV, montant/devise, géographie et dates de contrat (`contract_award`),
ainsi que le JSON des acheteurs et attributaires (`schema.py:74-98,154-197`).
La liste exhaustive des champs ignorés par chaque API est donc **non vérifiable
sans spécification/version des API sources** ; dans le code, tout champ qui n'est
pas projeté par les parseurs/mappers n'est pas stocké. Exemple explicite : TED
lit NUTS au parseur (`connectors/ted/parser.py:298-307`) mais `contract_award`
ne possède pas de colonne NUTS (`schema.py:184-196`).

`source_event.event_key` est la clé primaire et combine système, avis et version
(`schema.py:74-98`) : une correction est un événement distinct (`domain/events.py:167-174`).
Les DCE sont dédoublonnés par `(source_system, source_notice_id, source_url,
content_hash)` (`0036_procedure_documents.py:42-45`) et par clé SHA-256 dérivée
de ces quatre éléments (`documents/early_capture.py:108-154`).

Le DCE n'est pas écrit dans un bucket ni dans un chemin de fichiers par le code
actuel : `archive_content` est un `LargeBinary` et `blocks` un JSON dans
`procedure_documents` (`schema.py:101-139`; migration `0036...:19-45`).

Les archives ZIP sont développées pour extraction, mais le binaire ZIP d'origine
est conservé (`early_capture.py:219-233`). Cela permet de rejouer l'extraction

Le plan `docs/superpowers/plans/apres-mise-en-prod.md:25-40` décrit une future
sortie vers `/var/lib/kivou/dce`, mais c'est un plan, pas une implémentation :
aucune preuve ne permet de dire qu'elle a été réalisée.

Configuration de sauvegarde déclarée : dump PostgreSQL local quotidien à 03:17
(`kivou-backup.timer:2-8`), dans `/srv/kivou/backups` par défaut
(`ops/bin/kivou-backup.sh:25-28`), puis upload Restic « hors site »
(`kivou-backup.service:1-19`). Le script Restic retient 30 quotidiens,
12 mensuels et 3 annuels (`kivou-restic-upload.sh:179-197`). Les dumps locaux
de plus de 14 jours sont supprimés après succès (`kivou-backup.sh:160-182`).

La présence réelle de ces sauvegardes, l'emplacement Restic, leur caractère hors
hôte et un exercice de restauration effectué sont **non vérifiés**. Un runbook
décrit un restore drill (`ops/production/README.md:482-528`), mais une procédure
versionnée ne prouve pas son exécution. La relation de volume entre
`/srv/kivou/backups` et `/srv/kivou/source` est également **non vérifiée** : le
serveur n'est pas accessible ; le chemin `/srv/kivou/source` n'est pas déclaré
par les unités auditées. La perte antérieure du `.git` de ce chemin est donc un

## 3. Rétention effective

### Réponse explicite

**Un DCE joint à une attribution peut-il être supprimé aujourd'hui ? Non, par
la purge automatique DCE examinée.** La seule suppression trouvée dans le
corpus est :

```python
sa.delete(procedure_documents).where(
    procedure_documents.c.join_status == "unlinked",
    procedure_documents.c.expires_at.is_not(None),
    procedure_documents.c.expires_at <= now,
)
```

Source : `src/signals/documents/early_capture.py:188-196`, appelée avant chaque
passage DCE (`src/signals/ingestion/tender_notices.py:171-188`). Une jointure
forte écrit `join_status="linked"` (`early_capture.py:381-400`) et est donc hors
prédicat. Une jointure faible reste `review_required` (`early_capture.py:372-380`)
et n'est pas purgée non plus.

| Objet | Politique effective | Exemption / chemin de suppression |
|---|---|---|
| DCE `unlinked` avec date limite | expire 12 mois calendaires après `submission_deadline` | supprimé au prochain job DCE : `early_capture.py:99-105,188-196` |
| DCE sans date limite | `expires_at = NULL` | jamais supprimé par cette purge |
| DCE `linked` / `review_required` | aucun TTL appliqué par ce code | jamais supprimé par cette purge |
| archive brute + blocs du DCE supprimé | même ligne, donc tous deux supprimés ensemble | aucune archive externe prouvée |
| `account-purge` | efface les tables portant `account_id`, puis le compte, 24 h après demande | `accounts/data_rights.py:14-21,65-83`; les tables corpus n'ont pas `account_id` (`schema.py:74-247`) |
| dumps de sauvegarde locaux | 14 jours | `ops/bin/kivou-backup.sh:160-182` |
| snapshots Restic déclarés | 30 jours / 12 mois / 3 ans | `ops/bin/kivou-restic-upload.sh:186-195` |

Un AAPC sans attribution au bout de 12 mois devient : (a) son `source_event`
reste, car aucune suppression de cette table n'a été trouvée ; (b) ses DCE
`unlinked` datés sont supprimés ; (c) les DCE sans date limite restent. Cette
conclusion est une déduction du prédicat de purge et de l'absence de `DELETE`
sur `source_event` dans la recherche suivante, pas une observation production :

```text
$ rg -n --glob '*.py' 'DELETE FROM|sa\.delete\(' src
... src/signals/documents/early_capture.py:190: sa.delete(procedure_documents)...
... src/signals/accounts/data_rights.py:77-78: delete(... account_id ...)
```

### Requêtes de production à exécuter dès qu'un rôle `SELECT` est fourni

Elles sont **non exécutées** : accès production absent. Elles donnent les
chiffres demandés sans écrire de données.

```sql
-- inventaire et taille
SELECT relname AS table_name, n_live_tup AS estimated_rows,
       pg_size_pretty(pg_total_relation_size(relid)) AS total_size
FROM pg_stat_user_tables
WHERE relname IN ('source_event','contract_award','procedure_documents',
                  'evidence','opportunity_representation','ingestion_run',
                  'portal_capture_runtime')
ORDER BY relname;

-- avis, AAPC, attributions, lots, DCE, archives, blocs, exigences
SELECT
  count(*) FILTER (WHERE event_type = 'tender_notice') AS aapc,
  count(*) FILTER (WHERE event_type IN ('award_notice','award_correction','award_cancellation')) AS avis_attribution,
  (SELECT count(*) FROM contract_award) AS lots,
  (SELECT count(*) FROM procedure_documents) AS dce_tentes_ou_captures,
  (SELECT count(*) FROM procedure_documents WHERE archive_content IS NOT NULL) AS dce_archive_brute,
  (SELECT coalesce(sum(jsonb_array_length(blocks::jsonb)),0) FROM procedure_documents) AS blocs,
  (SELECT coalesce(sum(classified_requirements_count),0) FROM procedure_documents) AS exigences
FROM source_event;

-- couverture DCE, archive et provenance (la dernière mesure nécessite la forme réelle des blocs)
SELECT
  100.0 * count(DISTINCT pd.linked_award_key) / NULLIF((SELECT count(*) FROM contract_award),0) AS pct_attributions_avec_dce,
  100.0 * count(*) FILTER (WHERE archive_content IS NOT NULL) / NULLIF(count(*),0) AS pct_dce_archive_brute
FROM procedure_documents pd;

-- source, pays et mois de publication / attribution
SELECT source_system, source_country, date_trunc('month', published_on)::date AS mois_publication, count(*)
FROM source_event GROUP BY 1,2,3 ORDER BY 1,2,3;
SELECT se.source_system, date_trunc('month', ca.award_date)::date AS mois_attribution, count(*)
FROM contract_award ca JOIN source_event se USING (event_key)
GROUP BY 1,2 ORDER BY 1,2;

-- volume DCE capturé par mois ; byte_size est la taille logique, pas la taille PostgreSQL totale
SELECT date_trunc('month', captured_at)::date AS mois, count(*) AS dossiers,
       sum(byte_size) AS octets, pg_size_pretty(sum(byte_size)) AS volume_logique
FROM procedure_documents GROUP BY 1 ORDER BY 1;
```

Les pourcentages « blocs avec provenance complète », « titulaires résolus » et
« acheteurs résolus » ne sont pas calculables fidèlement avec le schéma seul :
la provenance bloc est un JSON sans contrat versionné de complétude, et
« résolu » n'a pas de statut corpus pour l'acheteur. Il faut d'abord fixer leurs
définitions et les colonnes de mesure.
